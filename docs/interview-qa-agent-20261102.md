## 0. 开场

### Q1：用 2 分钟介绍一下这个项目，以及你负责的部分。

**答：** 这是一个面向运维场景的故障诊断 Agent（AIOps Diagnosis Agent），核心是一个"检索增强 + 工具调用 + 人工审批"的诊断工作流，跑在 LangGraph 上。用户在 8001 端口的工作台描述故障，系统做混合检索（Qdrant 向量 + BM25 + RRF 融合 + DashScope 重排），把证据按行完整性组装后交给 Qwen 模型生成诊断，回答带可点击的引用角标；涉及建单时走 LangGraph 的 interrupt 做人工审批，批准后才真正创建工单。

我负责了三个层次的完整闭环：一是**业务链路**——从检索、证据工程、生成到 SSE 流式和审批；二是**可靠性工程**——所有真实模型调用前面有一套 JSONL 账本预算门控（预留-结算-fail closed），全程记录每一笔 token 消耗；三是**评测体系**——用真实 BGL 超算日志建了 43 题评测集，双模型裁判打分、跨家族复核、金标版本化更正，跑了基线、重排恢复、整改验证多个批次。

面试官可能追问"最难的点"，我会主动引到 §8 的故事：一个是 LangGraph 把未声明字段静默丢弃导致的引用错位，一个是分块残行压过完整原文导致的计数错误——两个都是离线测试过不了、必须到真实链路才暴露的问题。

## 1. 工作流与状态设计

### Q2：为什么用 LangGraph？直接用一段 Python 流程控制不行吗？

**答：** 有三个真实理由。第一，诊断流程不是线性的：检索后要判断相关性，不充分要改写查询再来一轮（最多一次），建单要在中途停下来**等人审批**——这个"暂停-恢复"用 LangGraph 的 `interrupt` + checkpointer 是原生支持的，自己写要做持久化中间态、幂等恢复，容易漏。第二，它强制我把流程状态收敛到一个显式的 `DiagState`（TypedDict），节点之间只通过状态传递数据，这让"生成器实际收到什么证据"这类问题可以被审计。第三，图结构让每个节点的事件（检索命中、工具调用、审批请求）可以逐个流式推给前端，而不是整图跑完才返回。

**追问：interrupt 恢复时怎么保证不重复建单？**
答：审批单先在数据库里原子落库（`prepare_approval` 节点），interrupt 携带 approval_id；恢复时服务端先做 CAS 式状态更新（`WHERE status='pending'` 的 UPDATE 判断 rowcount），重复请求会命中 409"审批已由其他请求处理"；工单创建有 approval_id 唯一约束兜底。审批决定和图恢复放在进程内锁里串行，单实例部署下避免并发恢复同一个 thread。

### Q3：你们的状态设计踩过什么坑？

**答：** 一个很典型的坑：LangGraph **只保留节点返回值里在 State schema 中声明过的字段**。我为了做引用修复，让 generate 节点返回了 `citations_indexed`（[n] → 第 n 条证据的逐命中映射），节点直调测试全对，但 SSE 的 final 事件里这个字段永远是空数组——因为我忘了在 `DiagState` 里声明它。更隐蔽的是前端逻辑：answer 事件里的映射是对的，final 事件用空数组**覆盖**了它，于是重复文档场景下角标悬停指错文档。后来我把"用真实编译图 invoke 到 final 再断言"写进了离线验证，不再信任节点直调测试。这个教训我总结为：**框架会替你做状态过滤，任何"多带出去"的字段都要在 schema 层登记**。

## 2. 检索与证据工程

### Q4：讲讲你们的混合检索。为什么又向量又 BM25？

**答：** 因为日志场景的两类查询正好落在两种检索的盲区互补上：**计数/行号类查询**（"L500-L534 里某消息出现多少次"）有精确词，BM25 强，向量反而会把数字语义模糊掉；**描述类查询**（"缓存奇偶校验错误怎么处理"）没有字面重叠，靠向量。两路各取 top-5，用 RRF（k=60）融合，再过一次 DashScope 的 text-rerank。检索强制带 tenant 过滤，多租户隔离在向量库过滤条件和 BM25 分桶两层都做了。

**追问：重排带来的收益怎么量化？**
答：我如实说——我们做了带重排和不带重排两个批次的对比（23 题重排批 vs 43 题无重排基线），但链路同时改了证据摘录策略，不是控制变量实验，所以**不宣称重排的独立增益**。能定量的是成本：重排单次实付约 5,200–7,500 tokens（5 个 2000 字符候选），我们按阿里云"query×候选数+文档总和"的成对计费口径做了上界预留。如果面试官追问"那重排要不要上"，我的回答是：按查询类型路由——计数/行号类查询 BM25 命中已经足够，重排花在描述类查询上更划算。

### Q5：日志是结构化程度很高的文本，你们怎么切分块？有什么坑？

**答：** 踩过的坑比方案本身更有讲头。最初的 chunker 是按字符滑窗（500–2000 字符），它会把一行日志**从中间切断**，于是模型会看到一条"行号只剩前几位"的残行。第一层修复是摘录时在行边界收口；但复审时发现还有第二层：**分块边界的残行会作为"独立证据"混进摘录**，甚至压过完整原文——我们的范围证据解析用 `setdefault` 先到先得，块尾截断行先出现就把完整行顶掉了，直接导致模型数出 33 条而真实是 35 条。最终方案分三层：chunker 改为完整行分组（无行界的散文回退字符窗）；行解析时按"是否以换行终止"标记完整性；范围证据以**租户文档全文为权威源**，命中块只做回退，残行显式计入 `targets_incomplete`。验证方式是把组装结果和语料原文**逐字对照**，全部范围题 0 残缺。

**追问：为什么不直接一行一个 chunk？**
答：一行信息量太薄，向量没有上下文会漂；而且 35 行一个窗口约 5,300 字符，按行切会产生 35 个 chunk，检索命中 5 个也只能覆盖 1/7 的窗口，计数题天然做不对。我们的结论是：**分块粒度要跟着查询形态走**——证据预算（每个 chunk 摘多少）和窗口完整性（范围题要整窗可见）是两个独立参数，我们最后拆成了 `evidence_excerpt_chars`（单块摘录上界）和 `evidence_range_chars`（范围组装上界）分别可配。

### Q6：模型怎么知道每条证据"是什么"？引用错位怎么防？

**答：** 生成提示词里要求答案用 `[n]` 标注，n 对应送给模型的第 n 条证据。关键是这个 n 的映射必须**从生成器一路同源透传**到前端：我们输出 `citations_indexed`（逐命中，重复文档保留各自 chunk 编号）给 SSE 和工作台，另存一个去重标题列表仅供展示。之前前端拿去重列表解释角标，重复文档时 42 处映射错位——修复原则就一句话：**角标的语义是"第 n 条证据"，不是"第 n 个文档"**。评测侧裁判看到的编号证据和生成器收到的也是同一份（从 answer 事件的 `used_evidence` 落盘直传），避免"裁判看到的比生成器多"这种评测失真。

## 3. 确定性与防幻觉设计

### Q7：LLM 数学不行，你们怎么保证"出现 35 次"这种数字是对的？

**答：** 原则是**模型解释、程序计算**。我们做了一个确定性的日志统计模块：对问题里的显式行范围（如 L500-L534）和可解析条件（行内精确子串、日志级别字段、时间范围），由代码直接在权威文档上计数，输出统计口径、命中行号清单、时间范围，并明确"只计完整行、同一行号只计一次"的 basis。这份结构化统计作为工具事件注入生成提示词，并要求模型"必须采用其数值，不得自行重新计数"。验证上，统计输出与语料逐行独立复算完全一致（比如 test-001 的 35 条、reg-003 的 25 行 FATAL 行号清单）。

**追问：问题里问"出现最多的消息"呢？**
答：这种要**先约定归一化口径**（哪些字段算变化字段）才能机器化，我们明确不支持——解析器把它列入 `unsupported`，回答里会如实说"需要您澄清统计口径"，而不是猜一个口径算个数。我认为这是 agent 设计里很重要的取舍：**确定性的部分程序化，模糊的部分澄清，而不是全推给模型或全写死规则**。

### Q8：怎么防止模型把"统计正确"说成"根因确认"？

**答：** 分两层。检索层把"相关"和"足以回答"拆开：grade 节点对范围题检查目标行覆盖，缺行就不判充足。生成层在系统提示词里写死了**根因三分法**——回答必须区分"已知事实 / 可能解释 / 仍需取得的证据"，并明确"统计正确不等于根因已证实"。有个真实对照：BGL 日志里 35 条都是 `instruction cache parity error corrected`（可纠正错误），真实批跑里模型会写出"疑似硬件隐患，但需要 BIST 诊断输出和不可纠正错误的出现才能确认，不建议仅凭日志执行更换"——这恰好是运维场景里最有价值的回答方式。裁判也按这个维度打分（appropriate_abstention 单独一项），那道题跨家族裁判三项全 true。

## 4. 评测体系

### Q9：你们的评测怎么做的？怎么防止"自己考自己"？

**答：** 数据集是真实 BGL 超算日志的 43 题（dev 10 / test 30 / 回归 3 单列），金标全部由原始日志行程序化推导并断言，不用人工标注的主观描述。判分用双裁判（qwen3.8-max-0902 主判 + qwen3.8-27b 第二判），两者看到**同一份答案、同一份 rubric、同一份编号证据**；分歧题追加 DeepSeek 做跨家族复核作为第三视角。自评偏差是明知道的，所以我们：披露主判与生成器同系列；缺判如实计 0 分单独披露；一致率只叫"双裁判一致率"，明确"非人工准确率、未做人工复核"。

**追问：金标自己错了怎么办？**
答：真发生过——复审发现两题金标与原始日志不符（一题时间戳是硬编码错的，一题把 17 条另一模板的消息混成同形式）。我们的处理是**版本化更正**：旧冻结集和旧成绩原样保留，发布带版本号的更正记录（gold_v2），每条更正附程序化推导依据和断言脚本；只对受影响题复判，更正前后分列。结果诚实地说：基线那两题在更正金标下**仍然双判错**（答案本身有事实错误）——更正是为了让评测正确，不是为了洗分。我认为这种"金标也要有版本管理和变更依据"的意识，是 LLM 评测和传统评测不一样的地方。

### Q10：评测发现模型答错，你怎么归因？

**答：** 用"证据是否完整"先切一刀。比如同样是计数题：整改前模型答 33 条，离线逐字对照发现它看到的证据里 L513/L525 是被切断的残行——这是**链路缺陷**，修复后重跑变 35 条，双裁判翻正；而另一道题证据 35 行全齐了模型还是错（把不同模板混同），那是**模型行为**，如实保留低分，不反复重跑刷分。我们的规则是"模型变化、证据变化、补判与回归分别标注"，任何分数都要能回答"这次和上次差异来自哪一层"。补判只调裁判不重新生成，成本和归因都干净。

## 5. 成本与预算治理（差异化亮点）

### Q11：真实模型调用很贵，你们怎么控制成本？

**答：** 我们把预算做成了**发送前的硬门控**而不是事后统计。所有真实调用通道（chat、tool_chat、embedding、rerank）统一走一个 JSONL 权威账本：请求前按保守上界预留（输入侧：UTF-8 字节数是字节级 BPE 下 tokens 数的可靠上界——但这只对输入成立，且我后来不再把它宣传成对所有模型的无条件数学保证；输出侧按请求实际携带、由服务端强制的 max_tokens 计入；有可计费推理 tokens 且不可关闭的模型（探针实测 qwen3.8-2.4t-a95b 强制思考）额外加推理预留；rerank 按官方"query×候选数+文档总和"的成对计费口径），响应后按供应商实报 usage 结算；缺 usage 记 `committed_unknown` 不记零；实报超预留自动 halt，要人工写 clearance 才恢复。跨进程用文件锁保证单写者。多进程（评测脚本 + 工作台）共享项目份额的方式是：启动时用"份额 − 兄弟账本已用"算本进程生效上限。截至 2026-11-01 的批次累计约 97 万 tokens 逐笔留痕、该阶段未知为零、未超限，审查方逐行重放过账本；后来一轮 glm-5.3 裁判调用超时产生 4.4 万 tokens 的 unknown（按预留额保守入账、不虚记零），并使项目总额触顶 fail closed——这个案例让我把'未知预留会挤占后续额度'也讲进预算设计里。

**追问：预留估不准会怎样？**
答：真实撞过两次墙。预留估小了，批跑到一半被自己的门控拒绝（fail closed 是设计行为，但对批跑是事故）——比如大窗口题的裁判载荷有 61 行摘录加答案体，实际预留要 1.5–2 万 tokens，我最初按 3,700 估的。修复是把预检公式和账本口径对齐（同一个估算函数），宁可提前跳题（`not_run` 如实披露）也不中途断。另一个方向是生效上限的坑：工作台进程启动时快照了兄弟账本用量，授权追加后不重启就会拿旧上限拒答——这些我都沉淀进了环境坑清单。

## 6. 工程与架构追问

### Q12：SSE 流式怎么做的？有什么注意点？

**答：** FastAPI StreamingResponse，图节点每产出一个事件（node_status/retrieval/tool/answer/approval_required）立即 yield，不等整图。注意点三个：一是 **ContextVar 不能跨 yield 保留**（SSE 的 next 可能在不同工作线程执行），运行记录的捕获要每次显式包一层；二是生成器内部自管 DB 会话，避免请求级会话在流式期间被提前关闭；三是错误语义——预算拒绝这类 fail-closed 要在流内发明确的 error 事件（含"请求未到达供应商"的提示），否则前端只看到断流，用户分不清是故障还是额度问题。

### Q13：多租户怎么隔离的？

**答：** 三层：JWT 里带租户和角色，API 层依赖注入校验；数据层所有表带 tenant_id；检索层向量查询强制 tenant 过滤、BM25 按租户分桶。有个真实的坑：服务启动的 warm-up 如果从 MySQL 重新分块建 BM25，会用默认 500 字符而和入库时的 2000 字符**分块边界漂移**——同一个内容在稠密臂和 BM25 臂变成两个不同边界的块，融合时互相干扰。修复是 BM25 重建直接从向量库 payload 滚动读取（`scroll_tenant`），保证两路**同源同界**，且非空集合零 embedding 消耗。语料入库也做了幂等（确定性 UUID 派生 point id，重复入库覆盖不重复计费）。

### Q14：模型调用失败怎么办？会静默降级吗？

**答：** 分模式。离线/开发模式有 MockLLM 规则实现，允许回退保证服务不中断；真实评测用 strict 模式——**预算拒绝、输出截断、JSON 解析失败都直接抛错**，绝不静默回退 Mock 冒充真实结果，失败留 attempts 痕迹。这个约束来自血泪教训：评测数据一旦混入降级输出，整批分数作废且难以察觉。唯一允许的"重试"是最多额外一次并逐题留痕。

## 7. 开放题

### Q15：这个项目如果继续做，你最想改什么？

**答：** 三件事，按 ROI 排序。第一，**按查询类型路由检索策略**：计数/行号类直接走"程序统计 + 文档权威读取"，跳过向量检索和重排，省钱且更准——统计模块已经证明这条路可行。第二，**人工校准的小标注集**：现在双裁判一致率 40+/43，但没有人工复核，我想标 50 题人工金标，量一量裁判和人的分歧集中在哪类题，再决定要不要换裁判策略。第三，**重排的控制变量实验**：固定其他条件单独开 关重排，把上一轮没敢宣称的收益量化出来。

### Q16：你觉得 Agent 开发和传统后端开发最大的区别是什么？

**答：** 两点。一是**输出的概率性**：传统后端同一个输入永远同一个输出，Agent 的每个环节都可能错，所以工程重心从"逻辑正确"移到了"证据可追溯 + 失败可归因"——我们连证据给模型的每个字符都要求可回溯到语料行号。二是**成本是运行时属性**：传统后端一次部署成本固定，Agent 每次调用都在花钱，所以预算门控、预留结算这类"财务级"的工程纪律要进代码路径。其他像评测驱动、prompt 即代码这些，本质是把测试文化和配置管理搬到 LLM 上，传统工程功底反而更有用。

## 10. 岗位匹配自查（面试前最后过一遍）

**能主动讲且有余量的**：LangGraph 状态机/interrupt/流式、混合检索与证据工程、确定性工具 vs 模型解释的分工、LLM-as-judge 评测与金标治理、成本门控。

**一句话定位**：做过"从检索、证据、工作流、审批到预算账本和双裁判评测全链路都有第一手实现与事故复盘"的 Agent 工程候选者。
